# rodf 단계별 진행 기록

> 이 문서는 **누구나 따라 읽을 수 있는 여정 기록**이다. 각 단계마다
> "무엇을 하려 했나 → 무엇을 했나 → 무엇을 배웠나 → 결과"를 풀어 쓴다.
> 실행 추적(대기열·완료 대장)은 [PROGRESS.md](PROGRESS.md),
> 설계 결정의 근거는 [DESIGN.md](DESIGN.md) 참조.

## 프로젝트가 무엇인가

**rodf**는 ODF 문서(.odt)를 LibreOffice와 **픽셀 수준으로 같게** 그려내는
Rust 라이브러리다. rdoc(doc), rdocx(docx), rhwp(hwp) 시리즈의 ODF 판이며,
세 가지 목적을 갖는다:

1. **ODT 파싱 → PDF/PNG 렌더링** 라이브러리 (LibreOffice가 정답 기준)
2. **MCFS** — 폰트가 없어도 레이아웃이 흐트러지지 않는 메트릭 호환 글꼴
   대체 (시리즈 전체가 공유할 핵심 차별 기능, 크레이트 `rmcf` 예정)
3. **통합 뷰어/에디터의 기반** — doc/docx, hwp/hwpx, odf를 한 곳에서
   보고 편집하는 구조 (멀티 백엔드 뷰어 셸이 첫 걸음)

## M0 — 엔진 분리성 스파이크

**질문.** rdocx의 레이아웃 엔진(oxml-layout: 폰트 로딩·셰이핑·줄바꿈)이
DOCX에 묶여 있지 않고 ODF에도 쓸 수 있는가? 이것이 성립하지 않으면
프로젝트 전체 계획이 무너지므로, 가정이 아니라 **검증**부터 했다 (D5·D7).

**한 일.** ODT 압축을 풀어 content.xml에서 문단 텍스트를 최소 파싱하고,
oxml-layout으로 셰이핑해 PDF 한 장을 만드는 수직 슬라이스를 구현했다.

**결과.** 성공. 엔진은 충분히 분리 가능했고, 여기서 워크스페이스 구조
(rodf-core 파서 / rodf-render 매핑 / rodf-cli)가 잡혔다. GitHub에
`emptinessform/rodf`로 공개(MIT OR Apache-2.0), README 한/영 병기.

## M1 — LibreOffice 오라클 (정답과의 거리 재기)

**질문.** "LibreOffice와 같게 그린다"를 감(感)이 아니라 숫자로 어떻게
판정하는가?

**한 일 — 오라클 v2 방법론.** 같은 문서를 LibreOffice와 rodf 양쪽에서
PDF로 만들고, **동일한 래스터라이저**(pdftoppm)로 이미지화한 뒤:

1. 크기 반올림 오차 정규화(crop) → 2. ±2px 위치 정합 → 3. 콘텐츠
영역만 크롭 → 4. 흐림(blur2) 후 SSIM 유사도 계산, **0.95 이상 = PASS**.

**배운 것 — LibreOffice의 관례를 실측으로 확정.** 문서 어디에도 안 적힌
LO의 실제 동작을 실험으로 알아냈다:

- 행 높이 = 폰트의 ascent + descent + lineGap, **lineGap은 행 위**에 얹힘
- 한글은 **어절(공백) 단위 줄바꿈** (공백 없으면 음절 폴백)
- 이탤릭 글꼴이 없으면 **20° 기울임 합성** (tan 20° = 0.36397)
- 행말 공백은 여백으로 넘칠 수 있음 (잉크 없음)
- 서양 글꼴(fo:\*)과 동아시아 글꼴(style:\*-asian)은 **속성이 분리**됨

이 관례들은 rdocx 포크의 엔진에 Word 동작을 깨지 않는 방식으로 랜딩했다.

**함정 하나.** 픽스처의 폰트명을 "Malgun Gothic"으로 썼더니 LO가 못 알아봐
Arial로 폴백 — 진단 전체가 오염될 뻔했다. **픽스처는 한국어 폰트명**("맑은
고딕")으로 쓴다는 규칙이 여기서 나왔다.

**결과.** 기본 매트릭스 코퍼스(폰트·크기·굵기·줄바꿈 조합 10문서)
**10/10 PASS**. side-by-side.png 데모 확보.

## M1.5 — 코퍼스 확장 + 결정론 + CI

**질문.** 우리가 만든 문서 10개 말고, **남이 만든 실전 문서**에서도
통하는가? 그리고 그 점수가 내 PC가 아닌 다른 환경에서도 재현되는가?

**한 일.**

- **와일드 코퍼스 50문서** — LibreOffice 저장소의 odfimport 테스트
  문서(버그 재현용 실전 파일들)를 태그 고정으로 수집, 파일별 sha256
  출처 대장([CORPUS-PROVENANCE.md](CORPUS-PROVENANCE.md)) 작성.
- **커버리지 감지** — 아직 렌더 못 하는 요소(표·프레임·목록·각주 등)를
  만나면 조용히 틀리게 그리는 대신 서브트리를 건너뛰고 **UNSUPPORTED로
  집계**한다. 스코어보드는 게이트가 아니라 현황판이라는 원칙.
- **결정론 오라클** — 배포판 LO는 버전이 흘러 점수가 무너진다는 것을
  확인(구식 LO 7.4에서 6/10으로 붕괴). Docker에 **TDF 아카이브 LO
  26.2.1.2 버전 고정** + Noto CJK 폰트셋으로 어디서든 같은 점수가 나오는
  환경을 만들었다.
- **CI** — Windows 빌드+테스트(ci.yml), 주간 Docker 오라클(oracle.yml).

**결과.** 첫 실전 성적 **32 PASS / 11 UNSUPPORTED / 7 FAIL**. FAIL 7건을
진단해 문단 정렬(fo:text-align), 빈 문단(`<text:p/>`) 소실, 커버리지
확장으로 해소 → **33 PASS / 16 UNSUPPORTED / 1 FAIL**(space.odt만 잔류).
결정론(noto) 프로파일도 10/10.

## M2 — rlayout 승격 (포맷 중립 엔진으로 독립)

**질문.** Word 에뮬레이션 엔진(rdocx-layout) 위에 ODF를 계속 얹을
것인가, 아니면 포맷 중립 층을 만들 것인가? (사용자 선택: **a — 승격**)

**한 일.** rodf 워크스페이스에 `crates/rlayout`을 신규 작성했다 —
포맷 중립 문서 IR(페이지·문단·런) + 플로우 레이아웃 엔진. **LO/ODF
관례가 기본값**이므로 Word 우회용 장치(font-natural sentinel 등)가
필요 없어졌고, DOCX 모델을 거치며 생기던 매핑 손실(MappingLoss)도
0건이 됐다. rodf 의존에서 rdocx 계열 크레이트가 사라지고 공유 하부층
(oxml-layout/oxml-pdf)만 남았다.

**의미.** 이 IR이 통합 뷰어/에디터(목적 3)의 공통 언어가 된다 —
ODF든 HWP든 DOCX든 프런트엔드가 IR로 기술하면 같은 엔진이 그린다.

**결과.** 스코어보드 10/10 유지한 채 전환 완료. 탭 스톱(기본 간격
파라미터화 + left/center/right 시맨틱)도 이 단계에서 구현.

## M2+ — 문단 내부 텍스트 모델 (와일드 마지막 FAIL 해소)

**질문.** 마지막 FAIL인 space.odt(0.68)의 원인 — 문단 안의 부분
서식(text:span)만 구현하면 되는가?

**아니었다.** 스팬을 구현해도 0.68 그대로. 렌더 이미지를 LO와 나란히
놓고 비교하며 **겹쳐 있던 결함 4개**를 차례로 벗겨냈다:

1. **text:span 문자 스타일** — 문단 안 일부 글자만 굵게/크게. 파서에
   스팬 스택(중첩 지원), 스타일 해석은 "문단 스타일 위에 스팬을
   바깥→안쪽 순서로 덮기", `Paragraph::spans()` API. *(0.68 그대로 —
   원인이 아니었음)*
2. **ODF 공백 병합 규칙** — 알고 보니 space.odt는 ODF 표준의 공백
   처리 적합성 테스트 문서였다. 문서 안 기대값 27케이스로 규칙을
   역산: 연속 공백은 스팬 경계를 넘어 1개로 병합, 문단 선두 공백
   제거, `<text:s>`는 무조건 공백 방출 + 병합 상태 리셋.
3. **엔티티 증발** — quick-xml 0.41이 `&lt;` 같은 참조를 별도
   이벤트(GeneralRef)로 주는데 처리하지 않아 `<span>`의 꺾쇠가 통째로
   사라지고 있었다. *(여기까지 0.686)*
4. **LO 내장 Heading + 문단 여백** — 스타일 정의가 없는 제목(text:h)에
   LO가 주는 내장 기본값(Liberation Sans 14pt×130%(H1), 굵게, 위
   0.42cm/아래 0.21cm)을 구현. 문서가 정의하면 문서가 이긴다.
   *(0.686 → 0.827)*
5. **문자 배경색** — fo:background-color를 행 높이 전체의 색 사각형으로.
   *(0.827 → 0.837)*
6. **LO 기본 탭 간격 = 2cm 실측** — LO가 만든 PDF의 좌표를 직접 파싱해
   확인: 문서에 탭 간격이 없을 때 LO의 프로그램 기본값은 1.25cm가
   아니라 **2cm**다(1.25cm는 LO가 문서를 저장할 때 명시하는 값일 뿐).
   이 과정에서 self-closing 요소의 탭 간격이 애초에 파싱되지 않던
   숨은 결함도 발견 — 폴백값과 문서값이 우연히 같아 테스트가 통과해
   왔던 것. *(0.837 → **0.9765 PASS**)*

**교훈.** 점수가 안 오르면 기능을 더 쌓지 말고 **이미지를 눈으로
비교**하라. 그리고 "테스트가 통과한다"와 "그 경로가 실제로 동작한다"는
다르다 — 폴백이 우연히 정답과 같으면 결함은 숨는다.

**결과.** 와일드 **34 PASS / 16 UNSUPPORTED / 0 FAIL / 0 CRASH**,
매트릭스 10/10 유지, 테스트 46개. (커밋 8c4392c)

## 곁가지 (본선 밖에서 확정된 것들)

- **MCFS 기획** — 한/글 FSL을 참조 용어로 두고 국제표준(PANOSE-1,
  CSS 폰트 메트릭 오버라이드) 기반의 범용 용어 **MCFS**로 확정.
  라이선스 4원칙(파일 비복제·외형 비추출·원본명 비사용·런타임 우선)을
  [mcfs-licensing.md](mcfs-licensing.md)로 정리. 구현은 M3 이후.
- **업스트림 기여** — tensorbee/rdocx 메인테이너 요청(이슈 #44)으로
  PR #45 제출. 후속 리뷰 대응은 발원지인 rdoc 워크스트림으로 인계.
- **포크 운영 규칙** — 엔진 개선(행간·기울임·한글 줄바꿈·탭 등)은
  emptinessform/rdocx 포크에 Word 무회귀로 랜딩하고 rev 고정으로 참조.

## 용어 풀이

- **오라클(oracle)** — 정답 기계. 여기서는 LibreOffice. 같은 문서를
  양쪽에서 그려 비교하는 심판 도구(tools/oracle.py)를 가리키기도 한다.
- **SSIM** — 두 이미지의 구조적 유사도(0~1). 0.95 이상을 합격으로 본다.
- **스코어보드** — 코퍼스 문서별 PASS/FAIL/UNSUPPORTED 현황판.
  게이트(막는 장치)가 아니라 현황 공개가 목적.
- **코퍼스** — 비교에 쓰는 문서 묶음. 매트릭스(우리가 만든 조합),
  와일드(LO 저장소의 실전 문서).
- **결정론** — 누가 언제 어디서 돌려도 같은 점수가 나오는 성질.
  LO 버전·폰트를 Docker로 고정해 달성.
- **IR (rlayout)** — 포맷 중립 중간 표현. 문서 포맷별 파서가 IR로
  번역하면 공통 엔진이 배치·렌더한다.
- **스팬(text:span)** — 문단 안에서 일부 글자에만 적용되는 서식 구간.
- **MCFS** — Metric-Compatible Font Substitution. 폰트가 없어도 글자
  폭·행 높이가 같은 대체 폰트로 레이아웃을 보존하는 기능.
